Agent Data Flow

Where every piece of data goes, how long it stays, who can read it, and how to delete it. Written for a security review — the uncomfortable parts are stated plainly rather than buried.

All data in-account Region us-east-1 6 places data rests Longest retention 90 days

The short version

A user's question travels through an authenticated API into a managed AWS runtime, is sent to a model inside AWS, and comes back as a written brief. Nothing leaves the AWS account or the region at any point — there is no third-party API call in the path.

The question, the model's answers, the agents' intermediate reasoning, and extracted facts about the user all come to rest in six AWS stores, each with its own retention. Trace data includes the full prompt and response text by default — that's the fact most likely to matter to a reviewer, and it's covered in detail below.

The part a reviewer will focus on: content in traces

Stated plainly, because the default is permissive

Agent observability works by recording what each agent did — and "what it did" includes the text it sent and received. By default the tracing library emits these as span attributes, unredacted:

  • gen_ai.input.messages — user messages, and tool inputs and results fed to the model
  • gen_ai.output.messages — model and agent responses
  • gen_ai.system_instructions — system prompts
  • gen_ai.tool.call.arguments and gen_ai.tool.call.result — tool inputs and outputs

So if a user pastes customer details into a question, that text lands in CloudWatch Logs, readable by anyone with logs access to the account, with no expiry unless you set one.

Three levers, with an honest trade-off:

The trade-off is real and worth a deliberate decision: the same content that makes traces useful for debugging and quality scoring is the content a reviewer will want restricted. A middle path that works well — keep content on, set a short log retention (7–14 days), and restrict CloudWatch Logs read access to the team that operates the service.

What memory keeps, and why it's different

Memory is the one store that derives new data rather than just holding what passed through. After a conversation, the service asynchronously extracts durable records into three namespaces:

NamespaceHoldsExample
/preferences/{actorId}/How this person likes to be served"plain language, under 150 words, bullets"
/facts/{actorId}/Things they told the agent about themselves or their work"is an account manager covering EMEA"
/summaries/{actorId}/{sessionId}/The gist of a past conversation"asked about memory pricing ahead of a customer call"

Two consequences worth naming. First, this data outlives the conversation and is injected into future prompts — so whatever enters memory will be seen again, by the same user, later. Second, it is keyed on actor_id, which makes that identifier a privacy boundary: a client that could choose its own actor id could read another person's preferences and facts. That is why it is taken from the verified JWT and never from the request body.

!
Decide what may enter memory before real users arrive, and enforce it in orchestrator.py. Customer names? Deal values? Health or HR details? Memory is the store most likely to accumulate something you didn't intend to keep.

Deleting one person's data

The runbook a privacy request will need

Everything is keyed on actor_id or user_id, so erasure is tractable — but it touches four stores and no single command does it.

# 1 · memory: list what exists for this actor, then delete the records
$ aws bedrock-agentcore list-actors --memory-id <MEMORY_ID>
$ aws bedrock-agentcore list-sessions --memory-id <MEMORY_ID> --actor-id <ACTOR>
$ aws bedrock-agentcore list-memory-records --memory-id <MEMORY_ID> \
      --namespace "/preferences/<ACTOR>/"
$ aws bedrock-agentcore delete-memory-record --memory-id <MEMORY_ID> --memory-record-id <ID>
#    repeat for /facts/ and /summaries/ ; delete-event removes raw turns

# 2 · the briefs themselves (prefixed by user)
$ aws s3 rm s3://<RESULTS_BUCKET>/briefs/<ACTOR>/ --recursive

# 3 · job rows (includes the prompt text)
$ aws dynamodb scan --table-name <JOBS_TABLE> \
      --filter-expression "user_id = :u" \
      --expression-attribute-values '{":u":{"S":"<ACTOR>"}}' \
      --query 'Items[].job_id.S' --output text
#    then delete-item for each

# 4 · logs and traces — the hard one
#    CloudWatch Logs cannot delete selected events. Options: wait out the
#    retention window, or delete the whole log stream/group.
✕
Step 4 is the gap. CloudWatch Logs has no per-record deletion, so content captured in traces can only be removed by letting retention expire or dropping whole streams. If you're subject to erasure obligations, this is the strongest argument for either a short retention window or switching content capture off.

Data in transit

  • User → API: HTTPS, JWT bearer token verified by API Gateway before any code runs. No AWS credentials on the client.
  • Inside AWS: every hop is an AWS API call over TLS — Lambda to SQS, Lambda to AgentCore, AgentCore to Bedrock, everything to CloudWatch.
  • Egress: the runtime is in PUBLIC network mode, which gives it outbound internet. Today it calls only AWS endpoints. Switch to VPC mode if policy requires egress control or the agent must reach private resources.
  • Cross-region: the model id us.anthropic.claude-sonnet-4-6 is a cross-region inference profile — requests may be served from another US region. If data residency is restricted to us-east-1, use a single-region model id instead.
!
That last point catches people out. A cross-region profile buys throughput and fewer throttles, at the cost of a residency guarantee narrower than "the US". Worth raising before a reviewer finds it.

Summary for the review form

QuestionAnswer
Does data leave AWS?No. No third-party API is called. Bedrock is an in-account, in-region AWS service.
Does data leave the region?Storage, no. Model inference may be served from another US region via the cross-region profile — changeable.
Is it used to train models?No. Bedrock does not retain prompts or completions.
Is it encrypted at rest?Yes, all six stores. Customer-managed keys available for Memory and CloudWatch Logs.
What's the longest anything persists?90 days (briefs in S3). Logs are unbounded until you set retention — do set it.
Can one user see another's data?No. Memory is keyed on an identifier taken from the verified token; job reads check ownership and return 404 on mismatch.
Can a user's data be deleted on request?Yes for memory, S3 and DynamoDB. Log and trace content can only be aged out or dropped wholesale.
Is PII filtered?Not yet. Bedrock Guardrails is the control, and should be attached before real user data flows.
