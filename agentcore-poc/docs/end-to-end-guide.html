Phase 1

Get it running

00

Open a session

CloudShell · every new terminal

CloudShell is already authenticated as your console identity — no aws configure, no access keys. But a reclaimed session drops you outside the virtualenv and the config, and that produces confusing errors three steps later.

$ cd ~/agentcore-multiagent-poc
$ source .venv/bin/activate          # prompt shows (.venv)
$ source deploy/config.env           # prints Account / Region / Agent
$ aws sts get-caller-identity

First time only, before the two source lines:

$ unzip agentcore-multiagent-poc.zip && cd agentcore-multiagent-poc
$ python3 -m venv .venv && source .venv/bin/activate
$ pip install -r requirements.txt pytest
$ python -m pytest -q tests/          # proves the agent logic with no AWS at all
3 passed
!
When CloudShell's upload gives you name-1.py or name_2.py, rename it onto the real filename before running. Running the numbered leftover means debugging a bug that was already fixed.
01

Enable the model

Console · Bedrock → Model access · us-east-1

Foundation models are opt-in per account and region. No IAM policy overrides this, and the failure arrives at step 07 rather than here.

  1. Bedrock console, region us-east-1 → left nav → Model access
  2. Modify model access → tick Anthropic Claude Sonnet → Next → Submit
$ aws bedrock list-inference-profiles --region us-east-1 \
    --query "inferenceProfileSummaries[?contains(inferenceProfileId,'sonnet')].inferenceProfileId"
[ "us.anthropic.claude-sonnet-4-6" ]
✓
If that id isn't listed, put one that is into MODEL_ID in deploy/config.env.
02

Turn on Transaction Search — and verify it

Script or Console · once per account+region

This converts OpenTelemetry spans into searchable span documents in the aws/spans log group. Without it, GenAI Observability is empty and Evaluations fails with "log events alone cannot be evaluated". Both failures are silent in the sense that nothing points at this setting.

$ bash deploy/01_enable_observability.sh
==> Allowing X-Ray to write spans into CloudWatch Logs
    resource policy in place
==> Switching trace segment destination to CloudWatch Logs
==> Waiting for the destination to report CloudWatchLogs (up to 5 min)
    Destination=CloudWatchLogs Status=ACTIVE
Transaction Search is ON.

# the check that actually matters — run it even if the script says it is fine
$ aws xray get-trace-segment-destination
{ "Destination": "CloudWatchLogs", "Status": "ACTIVE" }
✕
If it says "Destination": "XRay", Transaction Search is off no matter what any script printed. The usual cause is the CloudWatch Logs resource policy being too narrow — X-Ray needs the log group ARN both with and without the :* suffix, plus logs:CreateLogStream alongside logs:PutLogEvents. The current script grants exactly that. Console fallback: CloudWatch → Application Signals → Transaction Search.
03

Create the two IAM roles

Terminal · deploy/02_create_iam_roles.py

One role for the container to run as, one for Evaluations to read traces and call a judge model. Both trusted by the AgentCore service principal with source-account conditions. Re-running updates the policies in place.

$ python deploy/02_create_iam_roles.py
  created role multiagent-poc-runtime-role
  created role multiagent-poc-eval-role
  waiting 15s for IAM propagation...
✓
Both ARNs land in deploy/state.json — the file that threads every later step together. The 15-second wait isn't superstition: IAM is eventually consistent and creating a runtime with a role the control plane can't see yet is a classic CREATE_FAILED.
04

Create memory

Terminal · 2–3 min

One memory resource with three extraction strategies. Short-term (the raw turns) is automatic; the strategies turn conversations into durable preferences, facts and summaries, keyed on actor_id.

$ python deploy/03_create_memory.py
MEMORY_ID=multiagent_poc_memory-AbC123XyZ
05

Package the agent to S3

Terminal · no Docker required

AgentCore runs arm64 only. This downloads arm64 wheels rather than building an arm64 image, so the machine you're sitting at doesn't matter — which is why it works in CloudShell.

$ python deploy/04b_package_and_upload.py
==> Installing arm64 dependencies with uv
==> Zipping (files 644, dirs 755 as the service requires)
    deployment_package.zip: 38.9 MB zipped / 88.7 MB unzipped
==> Uploading s3://bedrock-agentcore-code-<account>-us-east-1/...
Saved code_bucket / code_key to deploy/state.json
!
Package after every code edit, not before. A zip built before your change deploys the old code, and the symptom is a fix that appears to have no effect.
06

Deploy the runtime

Terminal · 1–3 min
$ python deploy/05_deploy_runtime.py
==> Artifact: code s3://bedrock-agentcore-code-.../deployment_package.zip
==> Creating runtime research_orchestrator
  runtime: CREATING
  runtime: READY
READY  arn=arn:aws:bedrock-agentcore:...:runtime/research_orchestrator-XXXX  version=1
✕
"Agent artifact type cannot be updated" means the runtime was created from a container image and you're deploying a zip (or the reverse). The type is fixed at creation. Replace it with --recreate, or give the new one its own name with AGENT_NAME=…. Memory, roles and the dashboard are separate and survive either way.
!
After a recreate the runtime id and ARN change — so the log group changes too. Anything holding the old ARN needs the new one; state.json updates itself.

Invoke it

Terminal · 40–90 s for a full run
$ python deploy/06_invoke.py --actor am-dhilipan \
    "Customer call in 20 min — brief me on AgentCore Memory."
Invoking am-dhilipan / session-4a91... via DEFAULT  (40-90s)
  working... 45s
# AgentCore Memory — What You Need to Know
...
_Review score: 8.5/10 after 1 revision(s)._

session_id   : session-4a91…      review scores: [6.0, 8.5]
latency      : 41320 ms agent-side / 42.1s wall clock
  orchestrator  41320 ms   researcher  8210 ms
  writer        12470 ms   reviewer    6350 ms

Prove memory works — the part worth demoing. State a preference, wait ~90 s for extraction, then ask in a new session:

$ python deploy/06_invoke.py --actor am-dhilipan \
    "For every brief: plain language, no jargon, under 150 words, bullets."
# wait ~90s, then (no --session, so a brand new session)
$ python deploy/06_invoke.py --actor am-dhilipan "Brief me on AgentCore Runtime."
→ comes back short and jargon-free: that came from long-term memory
!
A first run that returns in seconds is usually small talk — the orchestrator answering directly without calling specialists. A real research run makes five model calls and takes 40–90 s. If it appears to hang with no output, check that deploy/common.py sets read_timeout=900 and disables client retries; the default 60-second timeout makes boto3 silently re-run the entire workflow.

Phase 2

Make it production

09

Replace the knowledge base — do this first

Code · agent/tools.py

Be clear-eyed about what you have: agent/knowledge_base.json is eight hand-written documents invented for the demo. The pipeline around it is production-shaped; its knowledge is not. Until this is real, everything else is scaffolding.

  • Bedrock Knowledge Base over your S3 documents — tools.py calls bedrock-agent-runtime:Retrieve instead of scanning a JSON file. Roughly 30 lines changed.
  • AgentCore Gateway if your sources are APIs rather than documents — it turns REST endpoints and Lambdas into agent tools with auth handled.
  • Keep the citation discipline. The [kb-003] tags exist so a human can verify a claim; with real sources they become links, and that is what makes output trustworthy enough to act on.
!
Also worth settling now: is "research and report" even your use case? The architecture — orchestrator, specialists, quality gate, memory — transfers to ticket triage or contract review unchanged. The prompts and tools don't. Swapping the task costs a day now and a rewrite later.
10

Create a prod endpoint you move deliberately

Terminal · deploy/08_promote_endpoint.py

Today every deploy is instantly live, because DEFAULT always follows the newest version. Fine when you're the only caller; wrong the moment users depend on it.

$ source deploy/config.prod.env
$ python deploy/08_promote_endpoint.py            # show versions and where prod points
$ python deploy/08_promote_endpoint.py --promote  # create prod, point at newest

# test the two paths independently
$ python deploy/06_invoke.py --endpoint DEFAULT --actor me "new version"
$ python deploy/06_invoke.py --endpoint prod    --actor me "what users get"

$ python deploy/08_promote_endpoint.py --rollback # undo in seconds

config.prod.env also pins MODEL_ID explicitly. A model version changing under you alters output quality with no deploy, and your eval baseline stops meaning anything.

11

Put a front door on it

Terminal · production/ SAM stack

One constraint shapes this: a brief takes 30–60 s, API Gateway gives up at ~29. So the request path cannot contain the agent call.

$ cd production && sam build
$ sam deploy --guided --parameter-overrides \
    AgentRuntimeArn=$(jq -r .agent_runtime_arn ../deploy/state.json) \
    AgentEndpoint=prod UserPoolId=$POOL UserPoolClientId=$CLIENT
!
Authenticate with the Cognito ID token, not the access token — the API Gateway JWT authorizer matches the aud claim, which only the ID token carries. A 401 here is almost always this.
✕
actor_id must come from the verified JWT, never the request body. Long-term memory is keyed on it, so a client that chooses its own actor id can read another user's remembered preferences and facts. One line in the submit Lambda; the difference between per-user memory and a shared bucket anyone can address.
12

Make the eval suite a release gate

CI · before every promote

The same input doesn't produce the same output, so you can't test this like normal code. A prompt change that fixes one case quietly breaks three others, and nobody notices until a user does.

  • Replace my four cases with 20–50 real requests and the answers your experts consider good.
  • Baseline the scores before any change ships, then fail the pipeline when they drop.
  • Add a feedback path — thumbs up/down written back to DynamoDB — and feed the bad ones into the eval set. That loop is what makes the system improve rather than drift.
  • Switch on online evaluation so live traffic is sampled too: the inputs you never thought of.
✓
Judging the trace rather than the answer is what lets ToolSelectionAccuracy and TrajectoryInOrderMatch catch a right answer reached the wrong way — a system about to fail on the next input.

14

The release loop, from here on

Every change, forever
# 1 · change code or prompts, then package and deploy to a new version
$ python deploy/04b_package_and_upload.py && python deploy/05_deploy_runtime.py

# 2 · test that version through DEFAULT — users are still on prod
$ python deploy/06_invoke.py --endpoint DEFAULT --actor me "..."

# 3 · gate: scores must hold against the baseline
$ python eval/run_eval.py

# 4 · promote. Users move. Rollback is one command if it goes wrong.
$ python deploy/08_promote_endpoint.py --promote

Numbers to watch once it's live: cost per brief, acceptance rate, p90 latency, and revision rate. A climbing revision rate means the writer prompt or the knowledge base has degraded — it moves before users complain.

A sensible pilot: weeks 1–2, real knowledge base and 5–10 users in Slack, measuring how many briefs get used versus discarded. Weeks 3–4, eval suite built from that traffic, alarms wired to a real channel, cost per brief established. Then expand — the architecture scales without redesign.
