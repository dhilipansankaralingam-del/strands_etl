The use case

A pre-call brief for account managers

The situation. An account manager has a customer call in twenty minutes and needs a short, accurate brief on a topic the customer raised — written the way they like to read it. Today that's fifteen minutes of searching an internal wiki and a rushed skim.

What the agent team does with it. The researcher pulls the relevant facts out of the knowledge base and tags each one with its source. The writer turns those into a structured brief for the stated audience. The reviewer scores it and sends it back once if it's thin. The orchestrator remembers that this particular AM wants plain language and 150 words, so the second brief already arrives in their format without being asked.

Why it fits this architecture. It's a task where the answer must be grounded (hence a researcher with a real source of truth and citations), where quality varies enough to need a gate (hence the reviewer), and where the same person comes back repeatedly (hence memory). Strip any one of those away and a single prompt would do.

✓
Everything below runs against the deployment you already have — no changes to the agent code.

Why this is the demo to show

It exercises all four capabilities in one pass, and each is visible in the output rather than asserted. Multi-agent — the per-agent breakdown shows four distinct workers. Quality gate — [6.0, 8.5] with one revision is the reviewer actually rejecting a draft, not decoration. Memory — step 2 proves long-term recall across sessions, step 3 proves short-term recall within one. Observability and evaluation — steps 4 and 5 below turn the same run into a trace and a score.

Run step 1 twice if you're demoing live and the preference doesn't take: extraction is asynchronous, and 90 seconds is a floor, not a guarantee.

Then watch what it left behind

  2. The dashboard. multiagent-poc-dashboard — per-agent latency and tokens, reviewer score, revision count. After one run it's a single point; after the eval suite it's a line.
  3. The score. python eval/run_eval.py --only memory-preference-recall re-runs the memory case and has AgentCore judge the real trace — including whether the agents ran in the right order.

Part 2

Triggering it in production

The constraint that shapes everything

A brief takes 30–60 seconds. API Gateway gives up at about 29. So the request path cannot contain the agent call — not as a tuning problem, as an architecture one.

The answer is to split the two: the API validates, records a job and returns 202 with a job id in milliseconds; a worker Lambda with a 15-minute ceiling does the slow call and writes the result somewhere the caller can fetch it. The queue in between buys retries, a dead-letter queue for failures, and a concurrency ceiling that doubles as a spend cap.

The two calls a client makes

# submit — returns in milliseconds
$ curl -X POST $API/briefs -H "Authorization: Bearer $TOKEN" \
    -H 'content-type: application/json' \
    -d '{"prompt":"Brief me on AgentCore Memory for a customer call."}'
{"job_id":"7c2f…","session_id":"brief-7c2f…","status":"QUEUED","poll":"/briefs/7c2f…"}

# poll — QUEUED → RUNNING → SUCCEEDED
$ curl $API/briefs/7c2f… -H "Authorization: Bearer $TOKEN"
{"job_id":"7c2f…","status":"SUCCEEDED","review_score":"8.5","revisions":1,
 "latency_ms":41320,"result_s3":"s3://…/briefs/am-dhilipan/7c2f….md"}

# follow-up turn: pass session_id back and you stay in the same conversation
$ curl -X POST $API/briefs -H "Authorization: Bearer $TOKEN" \
    -H 'content-type: application/json' \
    -d '{"prompt":"Shorten to 5 bullets.","session_id":"brief-7c2f…"}'

Deploy it with sam deploy --guided from production/, passing the runtime ARN out of deploy/state.json and your Cognito pool. Thirteen resources, one command.

Identity, sessions and actors

Three identifiers do different jobs, and conflating them causes either broken memory or a data leak.

IdentifierComes fromWhat it controls
actor_idThe verified JWT's sub claim — never the request bodyWhose long-term memory is read and written. Client-supplied means any user can read another's preferences and facts.
runtimeSessionIdGenerated per conversation; echoed back by the client for follow-upsWhich microVM serves the request, which short-term memory it sees, and which spans group into one trace. Minimum 33 characters.
job_idGenerated per requestThe polling handle. Ownership is checked on read, and a mismatch returns 404 rather than 403 so ids can't be probed.
Why the actor id is the one to get right

It is the only one of the three with a security boundary attached. Long-term memory is keyed on it, so it is effectively a tenant identifier — and it arrives as application data in the payload, which means the runtime cannot enforce anything about it. The enforcement has to happen in your code, once, at the edge: take it from the token the authorizer already verified and never read it from the body. A single line, and the difference between per-user memory and a shared bucket anyone can address.

Four ways to trigger the same runtime

The scheduled variant ships in the template, disabled. Flip Enabled: true on the Weekday0700 event and a brief lands every weekday at 07:00 UTC with no human involved. The event-driven variant is the same worker with a different event source — an S3 ObjectCreated notification or an EventBridge rule on your CRM.

Before you call it production

ConcernDo this
Blue-green releasesCreate a named runtime endpoint for prod and point the worker's AGENT_ENDPOINT at it. Deploys create a new version; promotion is repointing the endpoint, and rollback is repointing it back.
Release gateRun eval/run_eval.py in CI against the new version and fail the pipeline if scores drop. A prompt change that reads fine and scores worse is the failure mode this catches.
Quality in the wildTurn on online evaluation, and alarm on average ReviewScore — the template includes that alarm at a threshold of 7.
Cost ceilingWorker concurrency (10) caps parallel sessions; API throttling caps request rate; AWS Budgets on the Bedrock spend catches what neither does.
SafetyAttach a Bedrock Guardrail to the model calls for input/output filtering, and decide what may enter memory — it persists, and it will end up in future prompts.
Data retentionJob rows expire by DynamoDB TTL (30 days), briefs by S3 lifecycle (90), memory events by event_expiry_days (30). Set these to your policy, not mine.
Multi-environmentSeparate accounts for dev and prod, with the runtime, memory and bucket per account. Same artifact, different environment variables.
Secrets and configConfig in runtime environment variables; anything sensitive in Secrets Manager read at startup. Nothing in the image or the zip.
Supply chainPin dependency versions (the requirements file does), scan the image on push, and rebuild deliberately rather than on every deploy.
