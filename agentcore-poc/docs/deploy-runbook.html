Shortcut: run the whole thing in CloudShell

Console · terminal icon in the top bar
Why this step

Why this is often the fastest path. CloudShell already holds your console identity, so the entire credential problem disappears — no access keys to create, rotate or accidentally commit. For a POC, that removes both the most fiddly setup step and the most common way accounts get compromised.

The trade-off is the build environment: CloudShell is x86 and won't run the privileged container that arm64 emulation needs. That's precisely why the zip route exists — it downloads arm64 wheels instead of building an arm64 image, so the architecture of the machine you're sitting at stops mattering.

CloudShell is already signed in as your console identity — no aws configure, no access keys, nothing to install for the AWS calls. Every step here works in it except the Docker image build, because CloudShell is x86 and AgentCore needs arm64. Step 06 has a no-Docker path built for exactly this.

  1. Open CloudShell with the region set to us-east-1.
  2. Actions → Upload file → agentcore-multiagent-poc.zip.
  3. Unpack and install the script dependencies:
$ unzip agentcore-multiagent-poc.zip && cd agentcore-multiagent-poc
$ python3 -m venv .venv && source .venv/bin/activate
$ pip install -r requirements.txt
$ aws sts get-caller-identity   # already authenticated
✓
CloudShell keeps 1 GB in your home directory, so deploy/state.json survives between sessions. Idle sessions get reclaimed — when you come back, re-run source deploy/config.env and source .venv/bin/activate.
Why this shape

Why four agents instead of one good prompt. A single agent asked to research, write and critique in one pass does all three adequately and none of them well — the instructions compete for attention, and self-criticism in the same breath as composition is famously weak. Splitting the work gives each agent one job, a system prompt that says only that, and its own tool set. It also gives you a seam: the writer can be swapped for a cheaper model without touching the researcher.

Why agents-as-tools rather than a swarm. In this pattern the orchestrator owns control flow — it decides who runs, in what order, with what input. The alternatives (a swarm that hands off autonomously, a graph with fixed edges) trade that away for flexibility or rigidity respectively. Owning control flow is what makes the system observable: every delegation is a tool call, so the trace in step 09 reads as a clean nesting, and the trajectory evaluator in step 10 has something well-defined to check. Autonomous handoffs produce systems that are impressive when they work and very hard to debug when they don't.

Why the reviewer has a revision cap. A reviewer with no limit is an open-ended spend: each rejection costs another writer call plus another review. One revision captures most of the quality gain — the common case is a first draft missing one thing — while bounding worst-case latency and cost at roughly 5 model calls. The threshold (7/10) and the cap are both configuration, so you can tune the quality-versus-cost dial without touching code.

Why memory sits on the orchestrator only. The specialists are deliberately stateless: they get everything they need as arguments and return a result. That makes them trivially testable, safe to call concurrently, and cheap — none of them carries conversation history into its context window. Continuity is one agent's concern, not four.

00

Prerequisites on your laptop

Terminal · ~5 min
Why this step

Fail cheaply before you spend anything. The offline test runs the whole orchestrator → researcher → writer → reviewer loop against a scripted fake model, so prompt wiring, the revision loop and the response contract are proven before a single AWS call. Debugging that logic inside a container in the cloud costs minutes per iteration and real tokens; here it costs half a second.

The tool list isn't arbitrary. AWS CLI v2 is what the scripts borrow credentials from — boto3 reads the same profile. Docker is needed only for the container packaging route; the zip route skips it. Python 3.10+ because the code uses X | None type syntax and modern Strands. And the virtual environment matters more than it looks: the deploy scripts pin bedrock-agentcore and strands-agents versions, and installing those into your system Python is how you end up debugging someone else's dependency conflict at 11pm.

Unzip agentcore-multiagent-poc.zip and open a terminal in the project root. You need the AWS CLI v2, Docker with buildx, and Python 3.10+.

01

Turn on the Claude model in Bedrock

Console · Amazon Bedrock → Model access
Why this step

Bedrock ships with every model switched off. Access is opt-in per account and per region — a deliberate governance boundary, so an account can't accidentally start spending on a model nobody approved. Nothing in your IAM policy overrides it: the role can say bedrock:InvokeModel all it likes and the call still fails until the model is enabled.

Why an inference profile, not a plain model id. us.anthropic.claude-sonnet-4-6 is a cross-region profile: it routes each request to whichever US region has capacity. That buys you throughput headroom and fewer throttles for free, which matters here because one report fires five model calls in quick succession. It also explains the IAM policy's wildcard region on the foundation-model ARN — your request may well be served from a region you never named.

This step is first because it is the single most common failure in the whole runbook, and it fails late — at step 08, after everything else looks perfect.

The agents call Claude Sonnet through Bedrock. Model access is off by default in a fresh account, and this is the single most common cause of an AccessDeniedException later.

  1. Open the Bedrock console in us-east-1 → left nav, bottom group, Model access.
  2. Click Modify model access (or Enable specific models on a new account).
  3. Tick the Anthropic · Claude Sonnet row, then Next → Submit. Access turns to Access granted within a minute.

Then confirm the exact model id the code will call:

$ aws bedrock list-inference-profiles --region us-east-1 \
    --query "inferenceProfileSummaries[?contains(inferenceProfileId,'sonnet')].inferenceProfileId"
[ "us.anthropic.claude-sonnet-4-6" ]
✓
If that id is not in the list, copy one that is into MODEL_ID in deploy/config.env.
02

Load the config

Terminal · every new shell
Why this step

One place for names, one place for ids. config.env holds what you choose (region, agent name, repo name, model). deploy/state.json holds what AWS gives back (role ARNs, memory id, image URI, runtime ARN). Keeping those apart is what makes every later script runnable on its own and re-runnable without duplicating resources — step 07 doesn't ask you to paste a role ARN, it reads the one step 04 wrote.

It also means the teardown script knows exactly what to delete. A POC that can't be deleted cleanly is a POC that quietly bills you for months.

One file holds every name the scripts use. Sourcing it also looks up your account id and builds the ECR URI.

$ source deploy/config.env
Account=123456789012 Region=us-east-1 Agent=research_orchestrator
✓
Every later step assumes this line has been run in the current terminal. Re-open a tab → run it again.
03

Switch on Transaction Search (once per account)

Script or Console · CloudWatch → Application Signals → Transaction Search
Why this step

This is what turns telemetry into something you can actually read. The agent emits OpenTelemetry spans. Without Transaction Search those spans land as raw trace segments and stay effectively unqueryable; with it, they're ingested as structured logs into the aws/spans group, which is what the GenAI Observability view renders and — crucially — what AgentCore Evaluations reads when it judges a session. Skip this and step 10 has nothing to score.

Why 100% indexing for a POC. The default is 1%, which is right for production traffic and wrong for a demo: with a handful of test invocations, 1% sampling means you'll look for your trace and find nothing, then spend an hour wondering what's broken. Turn it down when traffic grows — indexed spans are the part you pay for.

It's account-and-region-wide and one-time, which is why it lives outside the per-agent scripts. The ~10 minute activation is also why it comes early: you do it now so it's ready by the time you first invoke.

This is what makes agent traces searchable — the GenAI Observability view and Evaluations both depend on it. Run the script, or do it in the console; they do the same thing.

$ bash deploy/01_enable_observability.sh
==> Allowing X-Ray to write spans into CloudWatch Logs
==> Sending trace segments to CloudWatch Logs (Transaction Search)
==> Indexing 100% of spans (POC setting)
{ "Destination": "CloudWatchLogs", "Status": "PENDING" }
!
Status shows PENDING at first and takes up to ~10 minutes to become active. Carry on with the next steps while it settles — just don't go looking for traces before it's done.
04

Create the two IAM roles

Terminal · deploy/02_create_iam_roles.py
Why this step

Two roles because two different services assume them. The runtime role is what your container runs as; the evaluations role is what the Evaluations service uses to read your traces and call a judge model on your behalf. Splitting them means the judge can never invoke your agent, and your agent can never read other people's traces — each one holds only what its job needs.

Why the trust policy looks paranoid. Both roles are trusted by a service principal (bedrock-agentcore.amazonaws.com), not by you — you never assume these roles. The aws:SourceAccount and aws:SourceArn conditions guard against the confused-deputy problem: without them, the service could in principle be talked into using your role on behalf of a resource in someone else's account.

What each grant actually buys, so you can trim it later:

  • ECR pull / S3 read — how the runtime fetches your artifact. One or the other, depending on the packaging route.
  • Logs + X-Ray — where stdout and spans go. Without these you get a runtime that starts and tells you nothing.
  • cloudwatch:PutMetricData, conditioned on namespace — the agent publishes custom metrics, and the condition means a bug (or a compromised dependency) can't write into other teams' namespaces.
  • bedrock:InvokeModel — the agents' actual work.
  • Memory actions, scoped to memory/* in your account — read and write conversation events and retrieve extracted records.
  • Workload identity — AgentCore issues each runtime an identity token; this is what lets it do that.

The 15-second sleep at the end isn't superstition: IAM is eventually consistent, and creating a runtime with a role the control plane can't see yet is a classic CREATE_FAILED.

The container needs a role to run under; Evaluations needs its own role to read traces and call the judge model. Re-running the script is safe — it updates the policies in place.

$ python deploy/02_create_iam_roles.py
==> IAM roles
  created role multiagent-poc-runtime-role
  created role multiagent-poc-eval-role
  runtime role: arn:aws:iam::123456789012:role/multiagent-poc-runtime-role
  eval role:    arn:aws:iam::123456789012:role/multiagent-poc-eval-role
  waiting 15s for IAM propagation...

In the console (IAM → Roles, filter multiagent-poc) the two roles look like this. Both are trusted by bedrock-agentcore.amazonaws.com, not by a user.

✓
Both ARNs are now written into deploy/state.json — that file is the thread running through every later step.
05

Create the memory store

Terminal · deploy/03_create_memory.py · 2–3 min
Why this step

The model has no memory; this is where the continuity comes from. Every invocation starts a model with zero recollection. Memory gives you two different things, and it's worth being precise about which is which.

  • Short-term = the raw turns of this session, replayed into the prompt. Cheap, exact, and gone when the session ends.
  • Long-term = records the service extracts asynchronously from those turns — preferences, facts, summaries — retrieved by semantic search in later sessions.

Why three strategies rather than one. They answer different questions. "How does this user like reports?" is a preference and should persist forever. "What did they tell me about their company?" is a fact. "What happened in that long session last Tuesday?" is a summary — you want the gist, not 40 turns replayed. Each lands in its own namespace so the orchestrator can retrieve just what's relevant instead of dragging everything into the context window.

Why actor_id is separate from session_id. The actor is the person; the session is one conversation. Long-term memory keys on the actor, which is exactly what makes the step-08 demo work: new session, same actor, preference still honoured. Get these confused and memory appears broken.

The async extraction is the trade-off to know about: it keeps invocation latency low, but it means a preference stated 10 seconds ago isn't in long-term memory yet. Hence the wait in the demo. Events expire after 30 days here — set deliberately, because conversation data you no longer need is a liability, not an asset.

One AgentCore Memory resource with three extraction strategies. Short-term memory (the raw turns) is automatic; the strategies are what turn conversations into durable knowledge.

$ python deploy/03_create_memory.py
==> Creating memory multiagent_poc_memory (2-3 min)...
MEMORY_ID=multiagent_poc_memory-AbC123XyZ
06

Package the agent — zip or container

Terminal · 1–8 min
Why this step

AgentCore runs arm64 only, which is the constraint driving this entire step. Graviton is cheaper per unit of compute, and the service standardised on it rather than supporting both.

Why two routes. They trade control against friction. The container route gives you full control of the runtime image — system packages, a specific Python build, anything you can put in a Dockerfile — at the cost of needing Docker and an arm64 build. The zip route hands packaging to the service: you supply Python files and wheels, it supplies the interpreter. For this POC — pure Python, no system dependencies — the zip loses you nothing and removes a whole class of setup problems.

Why the zip still works from an x86 machine. --python-platform aarch64-manylinux2014 tells the installer to download arm64 wheels rather than build for the local CPU. Nothing compiles, so the build host's architecture is irrelevant. The --only-binary=:all: flag makes that guarantee explicit: if a dependency has no arm64 wheel, the build fails loudly here rather than producing a package that dies on startup in the cloud.

The small details matter more than they should: file permissions (644/755) because the service refuses packages it can't read; main.py at the zip root because that's the path the entry point names; and opentelemetry-instrument in front of it because that wrapper is what auto-instruments the process so spans exist at all. Drop that one word and step 09 shows you an empty trace list.

A · Zip to S3, no Docker. The one to use in CloudShell, or on any machine without Docker. It downloads linux/arm64 wheels (downloads, not compiles — so your own CPU doesn't matter), zips them with the agent code and a root main.py, and uploads to s3://bedrock-agentcore-code-<account>-<region>/.

07

Deploy to AgentCore Runtime

Terminal · deploy/05_deploy_runtime.py · 1–3 min
Why this step

Why AgentCore Runtime rather than Lambda or Fargate. Agent workloads break the assumptions those services are built on. A single request here runs 40+ seconds and five model calls — past Lambda's comfortable zone and awkward against API Gateway's 30-second limit. More importantly, agent sessions are stateful: consecutive turns should hit the same execution context. AgentCore gives each session its own microVM with session affinity, sessions that can live for hours, and billing on active compute rather than wall-clock — so an idle session between turns costs almost nothing. You'd rebuild all of that yourself on Fargate.

The isolation is a security property too: one session's memory and filesystem are not reachable from another's, which matters the moment two real users share an agent.

Why the settings are what they are:

  • networkMode: PUBLIC — the agent needs to reach Bedrock and CloudWatch. Switch to VPC when it must reach private resources instead.
  • idleRuntimeSessionTimeout: 900 — hold the session 15 minutes after the last turn, so a user who pauses mid-conversation comes back to warm context rather than a cold start.
  • maxLifetime: 3600 — a hard ceiling, so a stuck session can't run forever on your bill.
  • Config in environment variables, not baked into the artifact — pointing at a different memory store or model is then a redeploy of config, not a rebuild. Same artifact promotes cleanly from dev to prod.

Why versions and a DEFAULT endpoint. Each deploy creates an immutable version; the endpoint is a pointer. Callers keep using the same ARN while you roll forward, and rolling back is repointing rather than rebuilding. This is also why re-running the script is safe — it updates in place rather than creating a second runtime.

This creates the runtime from whichever artifact you built last — the S3 zip or the ECR image (force either with --code / --container) — passes the memory id and model id in as environment variables, and waits until it reports READY. Run the same script again after any code change — it updates the existing runtime and creates a new version.

$ python deploy/05_deploy_runtime.py
==> Creating runtime research_orchestrator
  runtime: CREATING
  runtime: CREATING
  runtime: READY

08

Trigger it

Terminal, console Test pane, or CLI
Why this step

runtimeSessionId is the load-bearing parameter. It does three jobs at once: routes the request to the same microVM as the rest of the conversation, groups the spans so step 09 shows one trace instead of five unrelated ones, and keys short-term memory. The 33-character minimum is the service insisting on something with real entropy — a session id that collides is a conversation leaking into someone else's.

Why actor_id travels in the payload instead. The session is AWS's concept; the actor is yours. The runtime doesn't know or care who your users are, so identity for memory purposes is application data. In a real system this comes from your auth layer, never from the client.

Why the response carries more than the report. Returning review_scores, revisions and the per-agent latency and token breakdown means you can see the team's behaviour from the caller's side without opening CloudWatch — useful in a demo, and useful when something is slow and you want to know which agent is responsible before you go digging.

The three-command memory demo is the part worth rehearsing before you show anyone: step 1 states a preference, step 2 proves it survived into a new session (long-term memory), step 3 proves the current conversation is intact (short-term). Those are different mechanisms, and showing both is what makes the capability legible.

Three ways in, same runtime. The script is the easiest because it prints the per-agent breakdown.

09

Watch the agents work

Console · CloudWatch → GenAI Observability + your dashboard
Why this step

Logs don't work for multi-agent systems. When four agents and a dozen tool calls interleave, a flat log stream tells you what happened but not what caused what. A trace is the causal structure: the orchestrator's span contains the researcher's, which contains its tool calls. When a report comes back thin, the trace shows you whether the researcher found nothing, the writer ignored the notes, or the reviewer sent it back. Reconstructing that from logs is archaeology.

Why custom metrics on top of the built-in ones. AgentCore's own metrics answer operational questions — invocations, errors, throttles. They can't answer product ones: is quality drifting? which agent is burning the tokens? how often does the reviewer reject a first draft? So the agent publishes what only it knows — ReviewScore, RevisionCount, and latency and tokens tagged per agent. A rising revision count is an early warning that the writer prompt has degraded, visible long before anyone complains.

Per-agent token metrics are also how you find the cost. In this design the reviewer sees the entire draft on every call, which makes it a heavier consumer than its short output suggests — the kind of thing that's obvious on a chart and invisible in a total.

The dashboard exists so this is one link rather than a tour of five console pages. In a real deployment, alarms hang off exactly these metrics.

Create the custom dashboard, then open both views. The trace waterfall is where the multi-agent structure becomes visible — one span per agent, nested under the orchestrator, with the second writer call showing the revision loop.

$ python deploy/07_create_dashboard.py

GenAI Observability: https://us-east-1.console.aws.amazon.com/cloudwatch/home#gen-ai-observability/agent-core

10

Evaluate the team

Terminal · eval/run_eval.py · 10–15 min
Why this step

The same input doesn't produce the same output, so you can't test this like normal code. A prompt change that fixes one case can quietly break three others, and nobody notices until a user does. Evaluation replaces "it looked fine when I tried it" with a number you can compare across versions.

Why two layers. They catch different failures at very different costs.

  • Deterministic checks — keyword present, under the word limit, has headings and sources, reviewer approved. Free, instant, unambiguous. They catch the dumb regressions, which are most regressions.
  • LLM judges — helpfulness, faithfulness, goal success. They catch the things a rule can't express: a report that ticks every structural box and is still unhelpful, or one that invented a fact the research notes never contained.

Why judge the trace rather than the answer. Two of these evaluators can only work on traces: ToolSelectionAccuracy asks whether the orchestrator called the right specialist, and TrajectoryInOrderMatch asks whether the sequence was research → write → review. A right answer reached by the wrong path is a system that will fail on the next input, and output-only grading can't see it. This is why step 03 was a prerequisite, not a nicety.

Why the in-flight reviewer agent isn't enough. The reviewer is part of the system, using the same model, judging its own team's work with the context that produced it. Useful as a quality gate, worthless as an independent measurement — a model that fabricates a fact will cheerfully confirm it. Evaluations judge from outside, against your assertions.

On-demand versus online. On-demand is your regression suite: a fixed dataset, run before each release, comparable over time. Online samples live traffic, where the inputs are the ones you never thought of. You want both — one tells you whether you broke something, the other tells you what reality is doing to you.

Two layers. Deterministic checks run locally and cost nothing. Then AgentCore Evaluations judges the real trace of each run — including whether the agents were called in the right order.

11

Redeploy, then clean up

Terminal
Why this step

Redeploy is two commands because the artifact and the runtime are separate concerns. Build produces an immutable thing; deploy points the endpoint at it. That separation is what makes rollback trivial and what lets the same artifact move between environments with only environment variables changing.

Why cleanup is a script rather than a console tour. This POC creates resources across seven services, and two of them bill while idle — Memory retains records, ECR stores layers. A scripted teardown ordered correctly (online eval before runtime, runtime before memory) is the difference between a clean account and a slow leak you rediscover on next month's bill. It reads state.json, so it deletes exactly what was created and nothing else.

Transaction Search and the log groups are deliberately left alone — they're account-level settings other work may depend on, and log retention is usually someone else's decision.

Changed a prompt or added a tool? Two commands roll out a new version behind the same endpoint:

# zip route
$ python deploy/04b_package_and_upload.py && python deploy/05_deploy_runtime.py

# container route
$ bash deploy/04_build_and_push.sh && python deploy/05_deploy_runtime.py

And when the POC is done, delete everything it created — runtime, online eval, memory, ECR repo, dashboard and both roles:

$ python deploy/99_cleanup.py --yes
  deleted online eval
  deleted runtime
  deleted memory
  deleted ECR repo
  deleted dashboard
  deleted role multiagent-poc-runtime-role
  deleted role multiagent-poc-eval-role
✓
Costs while idle are near zero — runtime bills on active CPU/memory — but Memory records and ECR storage tick along, so run the cleanup when you're finished.
